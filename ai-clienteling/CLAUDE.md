# 프로젝트 컨텍스트: MCM 럭셔리 클라이언텔링 AI — "AI 2 (Clienteling/LLM)" 파트

## 너의 역할
너는 이 프로젝트에서 나의 개발 파트너다. 나는 코딩 초보이므로:
- 코드를 작성할 때마다 각 부분이 무슨 일을 하는지 짧게 설명할 것
- 한 번에 하나의 작은 단계씩 진행하고, 실행·확인 후 다음 단계로 넘어갈 것
- 복잡한 구조(클래스 남발, 과한 추상화)보다 읽기 쉬운 단순한 코드를 우선할 것
- 에러가 나면 원인을 초보자 눈높이로 설명할 것

## 프로젝트 개요
- 해커톤 제출작. 주제: "AI는 럭셔리 경험을 어떻게 혁신할 수 있을까" (MCM 브랜드 대상, Challenge 03: 360° 고객 경험)
- 핵심 컨셉: **"고객을 아는 AI가 아니라, 고객의 물건을 아는 AI"**
  - 제품의 미세 텍스처(가죽 결·스티치)를 개체 지문으로 등록 → AI가 고객이 실제 소유한 제품과 그 물리적 상태를 인지
  - 구매 이력 추측이 아닌, 보유 제품의 실제 상태 기반으로 상담·케어 제안
- 우리가 푸는 문제 (MCM이 직접 밝힌 페인포인트):
  1. 착장/장바구니까지 간 고객이 구매 없이 이탈 (전환 문제)
  2. 결제 이후 브랜드 접점 단절, 럭셔리다운 1:1 케어 부재 (engagement/LTV 문제)
- 타깃: 글로벌 디지털 노마드 Gen MZ. 매출 90%+가 글로벌/면세 → 다국어·여행 시나리오가 기본

## 내가 담당하는 범위 (AI 2 파트)
1. 상담 에이전트의 시스템 프롬프트 설계 (서비스의 "인격")
2. 지식 베이스: MCM 제품/헤리티지/케어 가이드 데이터 (JSON)
3. 응답 생성 로직: 입력(고객 정보+대화 이력+망설임 유형) → 프롬프트 조립 → LLM API 호출 → 답변 반환
4. 개인화 품질 검증 및 프롬프트 반복 개선

### 내 범위가 아닌 것 (만들지 말 것)
- 망설임 유형 분류 모델 (AI 1 담당 — 나는 분류 "결과"를 입력으로 받음)
- DB/데이터 저장 (Backend 담당), 채팅 UI (Frontend 담당), Persona Bot Lab (Integration 담당)
- 단, 로컬 테스트용 더미 데이터와 간단한 테스트 스크립트는 내가 만듦

## 에이전트 설계 원칙 (절대 규칙 — 에이전트 프롬프트 작성 시 반드시 반영)
1. **케어 우선(Care-first)**: 마모·컨디션 데이터가 있어도 교체/신제품 구매를 먼저 권하지 않는다.
   케어·수선을 먼저 제안하고, 교체는 수선 한계 도달 또는 고객이 먼저 물을 때만 언급.
   (이유: MCM의 핵심 가치가 Craftsmanship. "낡았으니 새로 사라"는 자기모순이자 감시감 유발)
2. **럭셔리 톤**: 쿠폰/할인/푸시 화법 금지. "부티크 어드바이저의 한마디" 톤.
   진단서 화법 금지 (예: "컨디션 71점, 임계 근접" ❌ → "사랑받은 흔적이 보여요, 케어를 도와드릴까요" ⭕)
3. **망설임 유형별 대응 전략** (AI 1이 분류해서 전달):
   - `fit` (사이즈/실용성 불안) → 실측·수납·무게 등 구체 정보
   - `price` (가격 대비 가치 확신 부족) → 헤리티지·장인정신 스토리텔링 (세일즈 토크 아닌 이야기로)
   - `timing` (재고/타이밍/여행 중) → 옴니채널 실행 제안 (타 매장 재고 홀드, 크로스보더 배송, 귀국 후 픽업)
   - `comparison` (타 브랜드 비교심리) → 비하 없이 MCM 고유 가치(비세토스, 모빌리티 DNA)로 차별점 제시
4. **개인화**: 보유 제품·컨디션 기록이 있으면 반드시 활용 (예: 실루엣 겹침 안내, 케어 이력 언급)
5. 다국어 대응 전제 (데모는 한국어 우선, 구조는 언어 확장 가능하게)

## 기술 스택 및 구조
- Python 3.x, OpenAI API (gpt-4o 계열) — 에이전트의 응답 생성(두뇌) 담당
- FastAPI — 개발 단계 5에서 팀 연동용 API 서버를 만들 때 사용 (그 전 단계에서는 불필요)
- API 키는 팀에서 발급받은 OpenAI 키를 .env 파일의 OPENAI_API_KEY로 관리, 코드에 하드코딩 금지
- .env 파일은 .gitignore에 반드시 포함 (키가 GitHub에 올라가면 안 됨)
- 데이터는 로컬 JSON 파일 (해커톤 규모에서 벡터DB 불필요 — 지식 베이스 전체를 프롬프트 컨텍스트에 포함하는 방식)

### 데이터 파일
- `products.json`  제품 6종 (치수·무게·소재·노트북 수납)
- `heritage.json`  브랜드 헤리티지 9절
- `services.json`  케어·수선·배송 정책. shipping 은 cross_border / domestic 으로 분리
- `customers.json` 더미 고객 10명
                   `recent_activity.intentional` (2026-08-17 추가) 이 접점이 고객이
                   **의도적으로 남긴 것**인지를 데이터가 들고 있다. 장바구니·문의·
                   착장 저장은 `true`, 단순 조회는 `false`. 이 값으로 언급 가능 여부가
                   갈린다 — "접점의 두 종류" 절 참고. 없으면 수동으로 본다.
- `stores.json`    매장 5곳 (서울 3, 부산 1, 도쿄 1). 한국어·영어 이름 병기
                   부산 롯데백화점 부산본점은 2026-08-15 사람이 직접 확인해 추가.
                   같은 날 센텀시티점이 **폐점**인 것도 확인됐다 — 웹 자료를 그대로
                   믿었으면 데모에서 없는 매장을 안내할 뻔했다. 수집 방식이 옳았다.
- `regions.json`   MCM 국가 사이트 29개국 + 주요 도시 90여 개의 도시-국가 매핑
                   (2026-08-15 추가) 고객이 말한 도시가 어느 나라인지 코드가 찾아
                   "매장을 아는 도시 / 영업국의 도시 / 목록 밖" 3층으로 응대를 나눈다.
                   **국가 사이트가 있다는 것과 그 도시에 매장이 있다는 것은 다르다.**
                   전 세계 매장 목록은 만들지 않았다. 로케이터가 부정확하고
                   폐점·팝업이 섞여 있어 확인이 불가능하며, 실서비스에서는
                   이 자리에 매장 조회 API가 들어온다.

### 입출력 인터페이스 (팀 합의 스펙 — 변경 시 이 문서 업데이트)
입력 (Backend/AI 1로부터):
```json
{
  "customer_id": "C001",
  "message": "고객 발화 텍스트",
  "conversation_history": [{"role": "user|assistant", "content": "..."}],
  "hesitation_type": "fit | price | timing | comparison | null",
  "owned_products": [
    {"product_id": "P003", "name": "Aren 토트", "purchased": "2023-05",
     "condition": {"overall": "good", "notes": "핸들 마모 진행"}}
  ]
}
```
출력:
```json
{
  "reply": "에이전트 답변 텍스트",
  "suggested_action": "care_booking | stock_hold | delivery | staff_connect | none"
}
```

`hesitation_type` (2026-08-18 계약 확정): 위 네 값에 더해 **팀 계약 라벨 5종**
(`SIZE_UNCERTAIN` / `PRICE_HESITANT` / `STYLE_DOUBT` / `STOCK_CONCERN` / `NONE`)도 그대로 받는다.
Backend 는 AI 1 출력을 변환 없이 넘기면 되고, `knowledge.LABEL_MAP` 이 우리 이름으로 옮긴다.
옛 값(`QUICK_EXIT` · `GENERAL_BROWSE`)은 계약에서 빠져 우리도 뺐다.
축이 다르므로 이름을 통일하지 않는다 — "AI 1 파트와의 축 차이" 절 참고.
**다만 대화 중(`/chat`)에는 이 값으로 전략을 고르지 않는다** — 같은 절 참고.
AI 1 이 함께 보내는 `hesitation_intensity` · `persona_tag` · `talking_point_hint` 는
우리 스키마에 없어 Pydantic 이 버린다. 보내도 무해하다.

`owned_products` 는 우리가 쓰는 필드만 통과시킨다
(`product_id` / `name` / `purchased` / `condition{overall,notes}` / `care_history`).
AI 1 이 보내는 `condition_score`·`risk` 같은 값은 `engine._clean_owned()` 가 걸러낸다.
프롬프트에 있으면 모델은 결국 인용하고, 그러면 "컨디션 71점, 임계 근접" 같은
진단서 화법이 나온다. 새 필드가 필요해지면 `OWNED_PRODUCT_FIELDS` 에 추가할 것.

`staff_connect` (2026-08-14 추가): 지식 베이스에 없는 정보를 고객이 물었을 때, 에이전트가
"매장 어드바이저에게 확인을 요청해드릴까요?"라고 제안하면 이 값을 반환한다.
Frontend는 "매장 어드바이저 연결 요청됨" 카드를 띄운다.
→ 추가 이유: 에이전트가 모르는 것을 인정하면서도 고객을 혼자 두지 않으려면, 그 제안이
   실제로 실행되는 액션이어야 한다. 이 필드가 없으면 "확인해드릴까요"는 지킬 수 없는 빈말이 된다.
   "AI가 다 아는 척하지 않고 사람에게 연결한다"는 장면 자체가 데모의 신뢰 설계 포인트.

2. [x] 지식 베이스 JSON 작성 및 프롬프트 주입
3. [x] 더미 고객 프로필 + 개인화 응답 확인 (보유 제품·컨디션 반영)
   - [x] (계획 외 추가) 에이전트가 먼저 말을 거는 기능 — `start_outreach()`
         고객이 물어야만 답하는 구조는 헬프봇과 같으므로, 착장·이탈·케어 시점을

4. [x] 망설임 유형별 응대 분기 + 케어 우선 톤 검증 (여러 시나리오 대화 테스트)
       gpt-4o-mini 로 튜닝 후 gpt-4o 로 재검증 완료
5. [x] 인터페이스 스펙대로 FastAPI 엔드포인트화 (Backend/Integration 연동용)
       - `POST /chat`     팀 합의 스펙 그대로. suggested_action 5종 전부 반환 확인
       - `POST /outreach` 에이전트가 먼저 말 걸기 (스펙에 없던 것 — 협의 필요)
       - `GET  /health`   서버·모델 확인
       - `POST /clienteling/reply` · `POST /api/chat` (2026-08-18) 통합 레이어 연동용.
         저쪽 HttpClientelingAdapter 가 이 두 경로를 순서대로 친다.
         condition_score 는 입구에서 버린다(진단서 화법 방지, _clean_owned 와 이중).
         `cited_asset_ids` 는 모델이 아니라 코드가 문자열 대조로 채운다 — 저쪽
         AS-\d{6} 정규식은 필드가 차 있으면 실행되지 않으므로 자릿수 문제가 우리
         경로에서는 사라진다. 인용에는 **시점 게이트**를 걸었다: 고객이 먼저 꺼낸
         제품이거나 케어 대화(care_booking)일 때만 인용한다. 인용은 Frontend 근거
         카드(컨디션 점수 표시)를 띄우므로, "케어 화제 전에는 컨디션을 가린다"를
         화면에도 적용한 것이다. 사이즈 문의에 실루엣으로 언급한 보유 제품까지
         인용하면 묻지 않은 마모·케어 권장이 카드로 들어간다.
         출처 추궁 턴에도 인용을 비운다 — 경계심을 표한 고객에게 마모 카드를
         보여주는 것은 원래 사고의 화면판이다.
         인용의 구별 토큰은 라인 이름(라틴 문자)만 쓴다 — "비세토스" 같은 공유
         서술어를 토큰으로 썼다가 다른 제품 문장에 걸려 엉뚱한 인용이 붙었다.
       - **"한 메종" 복원 (2026-08-18 저녁 — 현행 구조).** 통합 경로는 처음에
         별도 모드(integration.py, "요청의 target_product 만 아는" 구조)로 지었다가
         **폐기했다.** 팀 계약의 형식(제품 하나를 실어줌)을 구현하면서 그 전제
         ("어드바이저는 그 제품만 상담한다")까지 채택해버려서, 다른 제품을 물으면
         "정보가 없습니다", 재고·매장·픽업은 전부 확인 인수로 퇴화 — 우리 서비스의
         전제("어드바이저는 전 제품을 안다")가 사라졌다. 사용자 손 테스트가 드러냈다.
         **계약을 받아들일 때는 형식과 전제를 분리한다.** (경위는 DESIGN.md 2·6절)
         현행: `/clienteling/reply`·`/clienteling/outreach`·`/api/chat` 은
         **기존 MCM 엔진을 그대로** 부르되, 그 호출 동안만 `knowledge.load()` 가
         통합 데이터를 읽는다 (contextvars 오버레이, 파일명→대체 경로).
           · 세계관: 한 메종(=MCM 픽션). 제품 18종(MCM 6 + fixture 12 변환),
             고객 16명(C001~C010 원본 + CU-0001~0006 변환), 매장·재고·배송은 MCM 데이터
           · 통합 데이터는 `scripts/build_integration_data.py` 가 팀 브랜치
             fixtures 에서 **재생성** (사본 금지 — fixture 바뀌면 스크립트만 재실행)
           · C 고객의 자산 ID(AS-9…)·컨디션 점수는 시연용 가정값 (재고와 같은 계층)
           · `/chat`·`/outreach` 는 오버레이 미사용 → **바이트 단위 불변**
             (프롬프트 재료 스냅샷 해시로 증명. 동결은 말이 아니라 diff 로)
           · 인용(cited_asset_ids)=근거 카드: 고객이 먼저 꺼냄 / 케어 대화 /
             앞 턴에서 꺼낸 자산의 연속(카드 깜빡임 방지)일 때만. 추궁 턴은 차단.
             종류 단어는 한↔영 매핑(탑핸들↔Top Handle), 라인 공유 토큰(Aurelia)은
             구별 토큰이 아님(옆 자산 카드가 두 장 뜬 사고)
           · 오프닝 계기: session_events 의 의도적 접점(장바구니)과 자산 스캔
             기록(케어 접점으로 변환)만. 조회·체류는 옮기지 않음
         integration.py 는 미사용 폴백으로 보존 (docstring 에 폐기 사유).
         거기서 잡은 결함 7건(날짜 "작년" 계산, 자산 사이즈 지어냄, 수선 기간
         지어냄, 세일 단정, 무근거 입력, 통제권 누락, 라벨 주어 오독)의 수정은
         현행 구조에도 이어졌다 — 엔진의 기존 장치들이 같은 역할을 한다.
         검증: /chat 스냅샷 diff + mini 전체 12/12 + 4o 핵심 4종 + 전수 커버리지
         (fixture 12종 스펙 + 오프닝 14종) mini·4o 각 26/26 + 카드 게이트 6장면 × 2모델.
       - 실행: `uvicorn api:app --reload --port 8102` / 문서: `/docs`
         (8102 는 통합 레이어 app/config.py 의 clienteling_base_url 포트 배정)
       - engine.py 를 상태 없이 분리함. API 서버는 여러 요청을 동시에 받으므로
         전역 변수에 대화를 쌓으면 고객끼리 섞인다. 대화 기록은 부르는 쪽이 관리한다.
6. [x] 응대 전략 변형 버전 (Persona Bot Lab 실험용)
       `default` 균형형 / `storytelling` 서사 중심 / `practical` 수치·실행 중심 /
       `control` 대조군(우리 설계를 뺀 일반 상담 챗봇)
       - API: `POST /chat` 과 `/outreach` 에 `variant` 필드 추가 (생략하면 default)
       - 콘솔: `/storytelling` 처럼 입력해 전환
       - 비교 스크립트: `python tests/test_variants.py`
       - **대조군에는 사실만 준다.** 데이터 파일에 우리 응대 지침(agent_guidance,
         personalization_hooks 등)이 섞여 있어서, 그대로 주면 대조군도 케어 우선
         원칙을 따라간다. 실제로 그랬고, `strip_guidance()` 로 걷어내서 해결했다.

### 개발 중 얻은 원칙
- **프롬프트로 누르는 것보다 데이터 구조를 고치는 것이 강하다.**
  배송 선택지 나열(→ primary/alternatives), 매장 오안내(→ 코드에서 도시 결정),
  개인화 누락(→ personalization_hooks) 모두 데이터 수정으로 해결됨.
- **예시는 반드시 실제 데이터와 일치해야 한다.** 예시에 틀린 수치가 들어가면
  모델은 그 틀린 방식을 정답으로 학습한다.
- 톤 튜닝은 gpt-4o-mini(비용 1/20)로, 검증은 두 모델 다.
  **데모 모델은 gpt-4o (2026-08-18 mini 에서 전환).**
  8턴 스트레스에서 mini 가 직전 턴의 묻지 않은 제안에 다음 발화를 수락으로
  삼켰다(가격 부담 발화 → "수선 접수를 요청해두겠습니다", 5회 중 2회. 4o 는 0회).
  제출형 예선이라 심사위원이 길게 밀 수 있어 장턴 품질을 우선했다.
  분당 한도(30k 토큰)는 한 명씩 칠 때는 안 걸린다. 코드 기본값도 4o 로 바꿈.
- **데이터를 주는 것과 그 데이터의 사용 조건을 정하는 것은 별개다.**
  마모 정보를 컨텍스트에 넣어두고 "오프닝에는 쓰지 마라"는 조건을 빼먹었더니,
  에이전트가 첫 마디부터 "핸들이 닳으셨네요"라고 말했다. 버그가 아니라 규칙 공백.
- **날짜 계산처럼 실수가 잦은 판단은 코드가 하고 모델은 결과만 받는다.**
  매장 선택(도시 기준), 경과 기간("3년 전 이맘때"), 예산 대비 제품 분류가 그렇게 처리된다.
- **숫자 비교는 LLM에게 맡기면 안 된다.** 세 번 시도해서 코드만 통했다.
  ① 프롬프트 규칙 추가 → 실패 ② 가격순 정렬표 제공 → 실패
  ③ 코드가 예산을 추출해 '이내/초과'로 분류해서 전달 → 성공
  표를 줘도 모델은 "150만원 이하"에 145만원 제품을 "5만원 초과"라고 답했다.
- **프롬프트가 길어지면 앞쪽 규칙이 묻힌다.**
  지식 베이스 JSON 16,000자 뒤에 답변이 오다 보니, 앞에 적어둔 톤 규칙
  (빈 마무리 금지, 문장 수 제한)이 무시되기 시작했다.
  자주 어기는 규칙만 모아 `CORE_REMINDER` 로 프롬프트 맨 뒤에 다시 붙여 해결.
  망설임 전략이 잘 작동했던 것도 그것이 맨 뒤에 붙기 때문이었다.
- **턴 간 조건 누적은 코드가 기억해야 한다.**
  대화 기록을 다 넘겨도 모델은 앞 턴의 제약을 새 요청에 적용하지 않는다.
  ("125만원이 비싸다"고 한 다음 턴에 185만원 제품을 추천)
  agent.py 의 session 이 예산·가격 부담을 누적해 매 턴 다시 알려준다.
- **거절당한 제품을 다시 권할 때는 그 사실을 먼저 언급한다.**
  말없이 돌아가면 망각이고, 이전 발언을 언급하고 이유를 밝히면 재해석이다.
  후자는 앵커링 효과까지 얻는다.
- **프롬프트에 있으면 모델은 결국 인용한다. 말하면 안 되는 정보는 아예 가린다.**
  "핸들 갈라짐" 같은 컨디션 서술이 프롬프트에 있으면, 규칙으로 여러 번 막아도
  "보이네요", "심하다고 하셨으니" 로 계속 돌아왔다.
  → 고객이 상태를 언급하기 전에는 `condition.notes` 를 프롬프트에서 뺀다.
    없으면 인용할 수 없다. 대신 케어 이력을 근거로 삼아 오히려 더 나은 답이 나왔다.
- **재료를 전부 보여주면 해당 없는 것까지 쓴다.**
  오프닝 재료 세 가지(접점/케어 이력/시기)를 다 보여줬더니, 케어 이력이 없는
  고객에게 "3년 전 이맘때 봐드렸었죠"라고 지어냈다.
  → `pick_opening_material()` 이 이 고객에게 맞는 하나만 골라 보여준다.
- **답할 수 없는 주제는 코드가 감지해서 응대 틀을 준다.**
  방수·타 제품군·할인은 우리 데이터에 없다. "지어내지 마라"고 해도 모델은
  "어느 정도 저항할 수 있습니다", "세일을 진행하지 않습니다" 로 자리를 메웠다.
  → `UNANSWERABLE_TOPICS` 로 감지하고 응대 순서까지 지정한다.
- **붙이는 순서가 결과를 바꾼다.**
  새 블록을 뒤에 추가하면서 예산 분류가 앞으로 밀렸더니,
  "140만원 이하에 145만원 제품이 있습니다" 같은 모순이 나왔다.
  판단이 흔들리기 쉬운 것(예산 분류, 누적 조건, 망설임 전략)은 항상 맨 뒤에 둔다.
- **규칙이 많아지면 개별 규칙이 묻힌다.**
  CORE_REMINDER 가 18개까지 늘자 "빈 마무리 금지"가 지켜지지 않았다.
  → 자주 놓치는 셋만 골라 OUTPUT_FORMAT(진짜 마지막)에 다시 적었다.
- **규칙을 넣을 때 적용 범위를 확인해야 한다.**
  "마모를 먼저 꺼내지 않는다"를 오프닝 지침에만 넣었더니, 일반 대화에서
  케어 방법을 묻는 고객에게 "핸들에 마모가 보이는데"라고 답했다.
  같은 원칙이 필요한 자리가 여러 곳이면 공통 블록(고객 정보 규칙)에 넣어야 한다.
- **같은 지시를 매 턴 다시 넣으면 같은 답이 반복된다.**
  AI 1 이 매 턴 같은 hesitation_type 을 보내니, price 전략("헤리티지로 답하라")이
  매 턴 프롬프트 맨 뒤에 다시 붙어 세 턴 연속 같은 설명이 나왔다.
  프롬프트로 세 번 눌렀지만 실패했고, 구조를 바꿔서 해결했다.
  → 전략은 그 망설임이 **처음** 나타났을 때만 본문을 주입하고,
    두 번째부터는 "이미 대응했으니 반복하지 말고 이어가라"만 넣는다.
  대화 기록에 이미 그 전략의 결과가 있으므로 다시 지시할 필요가 없다.
- **JSON 모드에서 모델이 빈 객체를 돌려줄 수 있다.**
  화면에 `{}` 가 찍히고 대화가 끊겼다. 파싱 실패는 처리했는데
  파싱은 되지만 내용이 빈 경우를 놓쳤다. 한 번 재시도하고, 그래도 비면
  되묻는 문장으로 대체한다. (engine.py `_call`)
- **제약을 걸 때는 정당한 예외를 함께 정의해야 한다.**
  "서울 고객에게 도쿄 매장을 안내하지 마라"로 매장을 현재 도시에 잠갔더니,
  재고 확인까지 막혀서 "긴자에 없었다"는 고객에게 "긴자에 확인해줄까요"라고
  답했다. 옴니채널 시나리오(타 매장 재고 확인) 전체가 막혀 있었다.
  → 방문·픽업은 현재 도시로, 재고 확인은 전 도시로 분리해서 해결.
- **강한 예시는 그 패턴에 과적합된다.** "없을 때 프로토콜" 예시를 넣자
  조건을 만족하는 경우에도 "없습니다"로 답하기 시작했다.
  예시를 넣을 때는 반대 케이스(있을 때)도 함께 넣거나, 적용 조건을 명시해야 한다.
- **좋은 예시도 그대로 복사된다.** 나쁜 예만 조심하면 되는 줄 알았는데,
  보유 제품을 꺼내는 "좋음" 예시의 맺는 말이 서로 다른 세 고객에게
  거의 그대로 나갔다. 예시는 문장이 아니라 순서를 가르쳐야 한다.
  예시 뒤에 "여기서 배울 것은 순서다. 문장을 옮겨 쓰지 않는다"를 붙여 해결했다.
- **지시대명사는 이름 매칭을 뚫는다.**
  "대화에 이미 나온 제품은 빼라"를 제품 이름으로 걸렀는데,
  고객은 자기 가방을 이름으로 부르지 않는다. "이건", "제 가방"이라고 한다.
  그때 코드가 보유 목록에서 아무거나 골라 "구매 기록을 보니…"로 소개했다.
  → 지시대명사가 있고 이름이 없으면 제품이 특정되지 않은 것으로 보고,
    보유가 하나면 침묵하고 여럿이면 목록을 보여주며 되묻는다.
- **"하지 마라"만 있고 "무엇을 하라"가 없으면 모델은 아무것도 안 한다.**
  반복 금지를 넣었더니 고객이 "네"라고 했을 때
  "어떤 부분이 더 궁금하신지 알려주시면 안내드리겠습니다"만 돌아왔다.
  공을 넘긴 것이지 응대가 아니다. 금지 옆에 다음 걸음(조건 질문·대안 제시·미루기)을
  적어두자 해결됐다.
- **언어를 모델에게 맡기면 고유명사가 섞인다.**
  영어로 물은 고객에게 "at the 압구정 MCM 하우스 플래그십 스토어"라고 답했다.
  `languages` 필드가 데이터에 있었는데 코드 어디에서도 쓰이지 않고 있었다.
  → 응답 언어를 코드가 정하고(`detect_language`), 매장 데이터에 `name_en` 을 넣어
    번역이 아니라 선택이 되게 했다. 고유명사 번역은 모델이 지어낼 수 있다.
- **데이터에 적용 범위가 없으면 엉뚱한 곳에 적용된다.**
  `shipping.recommendation.primary` 는 "해외에서 본 제품을 한국에서 받는" 경우를
  위해 쓴 것인데, 범위 표시가 없어서 국내에서 이미 결제를 마친 고객에게도
  적용됐다. 배송이라는 선택지가 통째로 사라지고 픽업만 안내됐다.
  → `cross_border` / `domestic` 으로 나누고 각각 `applies_to` 를 붙였다.
- **제약에는 반드시 정당한 예외를 함께 정의한다 (두 번째 사례).**
  매장을 `current_location` 에만 잠갔더니, 싱가포르 고객이 "다음 달 서울 가는데
  거기서 받을 수 있나요"라고 물었을 때 서울 매장이 프롬프트에 없었다.
  모델은 매장을 댈 수 없으니 엉뚱하게 A/S 확인 이야기로 흘렀다.
  → 고객이 발화에서 직접 꺼낸 지역은 열어준다. 우리가 임의로 다른 도시를
    권하는 것과, 고객이 가겠다고 말한 도시를 안내하는 것은 다르다.
- **조건이 셋 이상이면 프롬프트는 반드시 진동한다.**
  재고를 어느 도시에서 확인할지에 조건이 셋이었다(현재지 / 고객이 없다고 말한 곳 /
  나중에 사겠다는 뜻). "현재지가 기본"이라 쓰면 고객이 없다고 한 매장을 다시
  확인하겠다고 하고, "귀국지 우선"이라 쓰면 눈앞의 매장을 두고 서울로 넘겼다.
  → `pick_stock_region()` 이 정하고 모델은 결과만 받는다.
  진동의 방향이 바뀔 때가 신호다. 규칙을 더 쓸 게 아니라 코드로 옮길 때다.
- **목록에 없는 것을 "불가"로 단정한다.**
  재고 확인 블록에 다른 도시 매장만 나열했더니
  "지금 계신 도쿄 긴자에서는 재고를 확인할 수 없습니다"라고 답했다.

  **판정만 하는 코드는 안정적이지만, 출력이 다시 모델을 거치는 코드는 아니다.**
  경미한 것을 잡으려다 대화가 어긋나는 결함을 만들면 교환비가 맞지 않는다.

  원칙의 이름을 정확히 기억해야 원칙을 잘못 적용하지 않는다.
- **점수 검사 문자열 같은 개별 검증보다, 사건이 재현되는 손 순서가 세다.**
  카드 파이프라인의 결함 셋(오프닝 인용 고정 빈값, 한영 종류 단어, 라인 공유
  토큰)은 전부 사용자가 화면을 눌러보다 나왔다.

### 재고를 데이터로 만든 이유 (2026-08-17)

손으로 돌려보다 이런 대화가 나왔다.

```
고객       > 결과 어떻게 나왔나요?
어드바이저 > 확인해본 결과, 재고가 없습니다.     ← 확인한 적이 없다
```

재고 API 가 없으니 모델이 지어냈다. 세 가지 선택지가 있었다.

1. 그대로 둔다 — 데모 흐름은 굴러간다
2. "모른다"로 막는다 — 옴니채널 시연이 죽는다
3. **데이터로 만든다** ← 이걸 골랐다

**고른 이유는 정직성보다 재현성이 컸다.**
지어내게 두면 리허설에서 "없습니다"였다가 발표 당일 "있습니다"가 나온다.
준비한 다음 대사가 안 맞는다. 시연에서 제일 곤란한 상황이다.

정직성도 걸린다. 매장 위치는 "확인해드리겠습니다"라고 하면서 재고만 아는 척하면
같은 성격의 정보를 다르게 다루는 것이라 **우리 주장 안에서 어긋난다.**
심사위원이 "매장은 모른다면서 재고는 어떻게 아세요?" 라고 물으면 답이 없다.

`stores.json` 의 `stock` 은 **시연용 가정값**이다. 제품·매장·헤리티지처럼
확인한 사실이 아니다. 세 층을 구분해서 말한다.

| 데이터 | 무엇인가 |
|---|---|
| 제품·매장·헤리티지·서비스 정책 | MCM 공식 자료를 직접 확인한 **사실** |
| 고객 10명 | 해커톤 규칙상 만든 **가상 인물** |
| 재고 | 시연을 위한 **가정값** |

**수량이 아니라 있음/없음으로 둔다.** "마지막 한 점입니다"는 희소성 압박이라
럭셔리 톤 규칙(푸시 화법 금지)에 걸린다.

넣고 나서 걸린 것들.

- **`services.json` 이 "실시간 재고 데이터 없음"이라고 말하고 있었다.**
  프롬프트가 스스로 모순됐다. 실시간이 아닌 건 여전히 사실이므로
  "시연용 가정값이며 실시간이 아니다"로 정확히 고쳤다.
- **제품별로 한 줄씩 늘어놓으면 다른 제품의 줄을 읽는다.**
  영어 응대에서 Aren(서울 두 곳 다 있음) 줄을 Stark 것으로 읽고
  "both locations" 이라고 답했다. 3/3 틀렸다.
  → 제품마다 제목을 달고 **상태별로 묶었다.** 줄이 짧아지고 섞일 자리가 없어졌다.
- **보유 제품을 조건 없이 뺐더니 고객이 물은 것까지 빠졌다.**
  C008 이 "Is the Stark backpack available in Seoul?" 이라고 물었는데
  본인이 Stark 를 가지고 있어서 표에서 빠졌고, 모델은 옆 제품 줄을 보고 답했다.
  → 고객이 직접 물었으면 보유 중이어도 보여준다. 하나 더 살 수도 있다.
- **말과 액션은 반드시 같이 간다.**
  "있는 곳을 알려드렸으면 액션은 stock_hold" 라고 조건 없이 적었더니,
  말로는 방문만 권하면서 액션만 stock_hold 가 붙었다(4/4).
  화면에는 보관 승인 카드가 뜨는데 고객은 그런 제안을 받은 적이 없다.
  → "실제로 여쭈었을 때만 stock_hold, 아니면 none" 으로 조건을 달았다.
- **동의를 받기 전에 진행하지 않는다.**
  1턴에서 보관을 여쭌 비율이 1/4 이었다. 나머지는 "가서 확인해보세요"로 끝내고
  고객이 "네" 하면 보관 요청을 넣었다. 고객이 동의한 것은 방문이지 보관이 아니다.
  → 마지막 문장으로 보관 요청 여부를 묻게 하고, 그때만 액션을 붙인다. 4/4 정합.
- **우리가 할 수 있는 것만 말한다.**
  "잡아두겠습니다"는 우리 데이터에 없는 서비스다(`services` 에는 `stock_check` 뿐).
  매장이 보관해 줄지는 우리가 정하지 못한다.
  → "보관 요청을 넣어두겠습니다 / 회신이 오면 알려드리겠습니다" 까지만 말한다.

**우리가 못 하는 것도 분명히 해둔다.** 결과를 고객이 되물어야 나오는 구조
(비동기 알림)는 Backend 몫이다. `/outreach` 에 사건 계기를 추가하면 시연은
가능하지만, 실제 이벤트 시스템은 우리 범위가 아니다.

### 접점의 두 종류 — 의도적 / 수동 (2026-08-17)

종전 규칙은 **오프라인은 말해도 되고 온라인은 안 된다** 였다. 선이 틀렸다.

실제로 갈리는 것은 **고객이 의도적으로 남긴 기록인가**이다.

| | 예 | 언급 |
|---|---|---|
| 의도적 | 장바구니, 위시리스트, QR 착장 저장, 문의, 구매, 매장 방문 | **가능** |
| 수동 관측 | 페이지 조회, 체류 시간, 몇 번 보았는지 | 불가 |

고객은 자기가 장바구니에 담은 것을 안다. 그걸 언급하는 것은 감시가 아니다.
오히려 모르는 척하는 편이 이상하다 — 담아둔 물건을 처음 보는 것처럼 소개하면
고객은 자기가 한 일이 어디로 갔는지 모르게 된다.

**종전 규칙이 우리 대표 시나리오를 막고 있었다.**
MCM 이 직접 밝힌 페인포인트 1번이 "착장/장바구니까지 간 고객이 구매 없이 이탈"인데,
C002(`온라인 장바구니 이탈`)에게 장바구니 이야기를 꺼낼 수 없었다.
규칙을 고치자 이렇게 열린다.
"Aren 스쿨 토트를 장바구니에 담아두셨네요. 무엇이 걸리셨는지 여쭤봐도 될까요?"

판정은 데이터가 들고 있다 — `recent_activity.intentional`.
유형 문자열에서 짐작하면 표현이 바뀔 때 조용히 깨진다.
**없으면 수동으로 본다.** 모르는 접점을 말해도 되는 쪽으로 기울이면,
실서비스에서 CDP 가 새 유형을 보낼 때 그것부터 새어 나간다.

같은 장바구니 고객이라도 **담았다는 사실**까지가 고객이 남긴 것이다.
그 안에서 치수를 몇 번 봤는지는 우리가 관측한 것이라 쓰지 않는다.

**AI 1 과의 관계도 여기서 정리된다.**
AI 1 은 클릭스트림(수동 관측)으로 분류하는데, 그것과 모순되지 않는다. 층이 다르다.

> **관측한 것으로 판단은 하되, 관측했다고 말하지는 않는다.**

AI 1 이 `QUICK_EXIT` 이라 판정해 우리가 먼저 말을 거는 것은 **행동**이고,
그 자리에서 "2회만 클릭하고 나가셨더라고요"라고 말하는 것은 **발화**다.
앞은 서비스고 뒤는 감시다.

적용 자리: `activity_is_intentional()`, `OPENING_MATERIAL["online_intentional"]`,
오프닝 지침의 관측 금지 블록, 마무리 질문 표.
담아두거나 문의한 고객에게는 **용도를 묻지 않는다.** 이미 고른 사람이므로
"왜 고르셨나"가 아니라 **"무엇이 걸리셨나"** 를 묻는다.

### 개인화와 감시의 경계 (이 프로젝트 최대 발견 — 발표 1순위)

고객이 말한 적 없는 Liz 쇼퍼를 에이전트가 언급하자 고객이 물었다.
"제가 Liz 쇼퍼 얘기를 했었나요?"

이 질문은 정보 확인이 아니라 **경계심**이다. "내 정보를 어떻게 아느냐"는 뜻이다.
개인화 서비스에서 가장 예민한 순간이고, 여기서의 답이 신뢰와 감시를 가른다.

당시 에이전트의 답이 최악이었다.
"3년 넘게 사용하고 계신 점을 기억하고 있었습니다. 핸들에 손길이 닿은 자리가 보이네요."
  · "기억하고 있었다" — 출처가 아니다. 무엇을 근거로 아는지 밝히지 않았다.
  · 경계심을 표한 순간에 **컨디션을 추가로 꺼냈다.** 불에 기름이다.
  · "보이네요" — 사진도 받지 않았는데 **관측을 사칭**했다.

세운 규칙
1. **출처 없이 보유 제품을 언급하지 않는다.**
   "현재 사용 중인", "갖고 계신"은 출처가 아니다.
   우리가 가진 출처는 구매 기록과 케어 접수 기록 두 가지뿐이며, 다른 경로를 지어내지 않는다.
2. **꺼낼 자리는 두 곳뿐이다.** 지금 질문에 완결된 답을 한 뒤 마지막 한 문장,
   또는 고객이 화제를 닫은 다음 턴. 답변 중간에 끼워 넣지 않는다.
3. **첫 언급은 사실과 열어두기까지만.** 마모·컨디션은 고객이 케어 대화에 들어온 뒤에.
4. **출처를 물으면** 사실 인정 → 출처 → 이유 → "원치 않으시면 더 드리지 않겠습니다".
   **밝힌 출처에서 바로 나오는 사실은 말해도 된다** (2026-08-17 정정).
   구매 시점·경과 기간처럼 방금 댄 근거의 범위 안에 있는 것은
   오히려 우리가 아는 만큼을 보여주는 것이라 신뢰에 도움이 된다.
   ("7년 동안 사용하신 것으로 알고 있습니다" — 같은 구매 기록에서 나오는 기간이다)
   흐리게 답하면 "얼마나 더 알고 있지?" 가 남는다.
   **금지되는 것은 종류가 다른 정보다** — 컨디션·마모, 다른 제품, 다른 경로.
   원래 사고는 정보가 하나 늘어난 것이 아니라 **상태 평가를 얹은 것**이었다.
   처음엔 "다른 개인 정보를 추가로 꺼내지 않는다"로 적어뒀는데,
   그대로 읽으면 정상 응대까지 위반으로 잡힌다. 실제로 한 번 잘못 잡았다.
   끌 수 있는 설정 기능이 있다고 말하지 않는다. 그런 기능은 없다.
5. 컨디션 언급 조건 (a)는 고객이 **상태**를 말한 경우다.
   제품 **이름**이 발화에 등장한 것만으로는 충족되지 않는다.
6. **꺼낼 화제가 아니면 아예 보이지 않게 한다** (2026-08-15 추가).
   위 1~5는 "어떻게 말할지"의 규칙인데, 케어와 무관한 턴에서는
   "말할지 말지"부터가 문제였다. 재고를 묻는 고객에게 케어를 얹는 일이
   규칙을 세 번 조여도 반복됐다.
   → 케어 화제가 아닌 턴에는 구매 시점·케어 이력·경과 기간을 프롬프트에서 가린다.

프롬프트만으로는 진동했다. 느슨하면 출처 없이 꺼내고, 조이면 아예 꺼내지 않았다.
→ `build_owned_bridge()` 로 해결. 고객 질문이 A/S·케어 화제이고 보유 제품이 있으면,
  코드가 "구매 기록을 보니 2023년 5월에 들이신 Liz 쇼퍼" 라는 **출처가 붙은 표현까지
  만들어서** 넘긴다. 꺼낼지 말지를 모델 판단에 맡기지 않는다.

Persona Bot Lab 제안: **프라이버시 민감형 페르소나**(개인화에 경계심을 보이는 고객)를
페르소나 축에 추가하면 이런 사고를 시뮬레이션 단계에서 잡을 수 있다.
회귀 테스트는 `tests/test_privacy.py`.

### 톤 설계에서 발견한 것 (발표 재료)
- **요청하지 않은 상태 평가는 케어가 아니라 감시다.**
  같은 문장도 누가 대화를 열었느냐에 따라 배려가 되기도, 감시가 되기도 한다.
  고객이 사진을 보내 진단을 요청한 직후의 "핸들에 사용감이 보이네요"는 케어지만,
  요청 없이 먼저 꺼내면 지적이 된다.
- **명분이 달라지면 같은 제안이 다르게 들린다.**
  "가방이 낡으셨으니"(지적) / "계절이 바뀌었으니"(배려) / "전에 봐드렸으니"(관계)
- **개인화의 강도는 "이 말을 다른 고객에게도 똑같이 보낼 수 있는가"로 판별된다.**
  계절 인사는 모두에게 보낼 수 있고, 케어 이력은 이 고객에게만 할 수 있는 말이다.
- **모르면 묻는 데서 그치지 않고 확인을 인수한다.**
  매장 정보가 없는 지역의 고객에게 "가까운 매장에서 접수하세요"는 안내가 아니라 회피다.
  매장 이름을 지어내지도, 모른다고 끝내지도 않는다.
  "그 지역 매장은 확정해드리기 어렵습니다. 매장 확인과 함께 접수를 넣어드릴까요?"
  → 모른다는 사실은 숨기지 않으면서 고객의 일은 진행된다.
  실서비스에서는 이 자리에 매장 조회 API가 들어온다.
- **말의 주어는 제품이 아니라 고객이다.**
  "고객의 물건을 아는 AI"를 만들다 보니 에이전트가 물건에게 말을 걸고 있었다.
  "핸들을 봐드렸던 Pina, 잘 지내셨나요?"는 가방에게 안부를 묻는 문장이고,
  "Pina 토트, 정말 멋졌습니다"는 제품 칭찬이다.
  안부는 고객에게 묻고, 멋진 것은 제품이 아니라 그것을 든 고객이다.
  물건을 아는 것과 물건에게 말하는 것은 다르다.
- **두 고객에게 똑같은 문장이 나갔다면 개인화에 실패한 것이다.**
  "오늘 보신 그 토트"는 누구에게나 할 수 있는 말이다.
  매장 이름과 라인 이름을 넣어야 이 고객에게만 하는 말이 된다.
- **나쁜 예를 문장으로 적으면 모델이 그 문장을 따라 쓸 수 있다.**
  금지하려고 적어둔 "Pina, 잘 지내셨나요?"가 그대로 출력됐다.
  나쁜 예는 인용 가능한 문장 대신 설명형으로 쓰는 편이 안전하다.
- **시스템의 사정을 화면에 늘어놓지 않는다.**
  말 걸 계기가 없는 고객을 막았더니, 오류 문구가 `어드바이저 >` 자리에 찍혔다.
  자리를 `[시스템]` 으로 옮겼는데도 여전히 나빴다.
  "착장·조회·구매 기록이나 보유 제품 중 하나는 있어야 합니다" 는

| `PRICE_HESITANT` | `price` |
| `STYLE_DOUBT` | `null` (뜻이 우리 `fit` 과 다름 — 미적 고민에 치수로 답하면 안 된다) |
| `STOCK_CONCERN` | `timing` |
| `NONE` | `null` |

**축이 상당 부분 맞춰졌다.** 옛 라벨 넷은 셋을 `null` 로 흘려보내야 했는데,
새 계약은 둘이 정확히 겹친다. 이제 안 오는 것은 `comparison` 하나뿐이다.

> **종전에 여기 "우리 `fit`·`timing` 은 클릭 로그에 남지 않아 원리적으로 불가능하다"고
> 적어두었는데, 그건 옛 라벨 집합에 대해서만 참이었다.**
> 계약 예시를 보면 `size_guide` 이벤트에 어느 치수를 얼마나 오래 봤는지가 남는다
> (38 을 88.5초, 38.5 를 61초 → 장바구니). 사이즈 불안은 로그에 남는다.
> 우리가 축 차이를 지적했더니 상대가 축을 맞춰온 것이다.

**옛 라벨 (기록용)** — `QUICK_EXIT`(세션 클릭 2회 이하, 19.7%)과
`GENERAL_BROWSE`(그 외, 27.7%)는 계약에서 빠졌다.
모르는 값은 `normalize_hesitation()` 이 `None` 으로 흘리므로 흘러들어와도 안 깨진다.

#### 그런데 대화 중에는 이 값으로 전략을 고르지 않는다 (2026-08-18 결정)

계약이 넓어졌으니 `fit`·`timing` 전략도 AI 1 이 켜주면 좋겠지만, **반대로 갔다.**

AI 1 분류는 **세션 단위**라 고객이 채팅에서 한 마디도 안 해도 값이 오고,
매 턴 같은 값이 온다. 그 값으로 전략을 붙이면 하지 않은 말을 확인해주게 된다.

  · `price` → "가격이 마음에 걸리시는군요" — 부담을 말한 적이 없다
  · `fit` → 치수·수납·무게를 쏟는다 — 사이즈를 물은 적이 없다
  · `timing` → "서두르지 않으셔도 됩니다" — 조급해한 적이 없다

셋 다 "제가 그런 말을 했었나요?" 를 부르는 형태다. **출처 추궁과 같은 감시 문제다.**

전에는 `price` 에만 게이트를 두어 "고객이 가격을 말했는가"를 확인했다.
계약이 바뀌자 게이트를 셋으로 넓히려 했는데, `fit`·`timing` 은 뽑아낼 숫자가 없어
**발화의 화제를 단어 목록으로 맞혀야** 했다.
만든 목록이 첫 시험에서 `"모레 귀국이라"`(우리 대표 시나리오 발화)를 놓쳤다.
`LATER_HINTS` 에 `귀국해서/귀국 후/귀국하고/귀국하면` 은 있는데 `귀국이라` 가 없어서다.

→ **판정할 필요를 없앴다.** `engine.pick_strategy()` 가 한 곳에서 정한다.
  AI 1 라벨은 대화 중 전략을 고르지 않고, 발화가 고른다.
  발화로 확실히 뽑히는 것은 지금 가격 부담 하나뿐이다 (금액은 숫자로 뽑힌다).

역할 분담은 원래 적어둔 그대로다. 발표에서 물으면 이 문장으로 답한다.
  · **AI 1 = 대화 시작 전 세션 신호** (누구에게 언제 먼저 말 걸까) → `/outreach`
  · **대화 중 망설임 = 발화에서** → `/chat`

> **관측한 것으로 판단은 하되, 관측했다고 말하지는 않는다.**

`hesitation_type` 이 `null` 이어도 대화는 정상이다. 답을 만드는 장치들
(제품 상세, 노트북 수납표, 매장 안내, 재고 표, 보유 제품 브릿지, 예산 분류)이
전부 **고객 발화**를 보고 붙기 때문이다. 시연에서 손으로 넣을 일이 없다.

**`/outreach` 의 각도는 `STYLE_DOUBT` 하나뿐이고, 새 라벨에도 추가하지 않았다.**
기준이 하나로 정리된다 — **각도는 "질문을 좁히는" 형태일 때만 안전하다.**
"답을 미리 내미는" 형태면 아직 한 마디도 안 한 고객에게 관측을 말하는 것이 된다.
`STYLE_DOUBT`(무엇에 쓰실 건지)만 질문이고, 나머지 셋은 전부 답이다.
`PRICE_HESITANT`(→ 광고가 된다)와 `QUICK_EXIT`(→ 없던 내용이 생긴다)에서
같은 이유로 두 번 실패한 기록이 `OUTREACH_ANGLE` 주석에 있다.

**계기 신호는 잃었다.** `QUICK_EXIT` 이 빠지면서 "지금 먼저 말 걸 고객"을
골라주던 값이 없어졌다. 코드는 안 깨진다 — `/outreach` 의 계기는 `recent_activity`
(착장 저장·장바구니·케어 시점)가 정하지 이 라벨이 정하는 게 아니었다.
`HANDOFF.md` 2번에 "다른 필드로 받을 수 있는지" 로 적어 팀에 넘겼다.

**AI 1 에 알린 것 (우리가 못 고치는 것):**
- `hesitation_intensity` 가 `predict_proba[:, 1]` 이라 **구매 확률**로 나온다.
  값이 높을수록 살 가능성이 높은데 이름은 망설임 강도다. 화면에 쓰면 반대로 표시된다.
- `talking_point_hint` 의 `교체_시점_제안` 은 우리 절대 규칙 1번(케어 우선)과 반대다.
  조건 판단은 맞으므로 값 이름만 `케어_제안` 으로 바꾸면 맞는다.
  우리 스키마에 없어 Pydantic 이 버리므로 응답에는 영향이 없다.
  다만 **Frontend 가 이 값으로 카드를 띄우면 화면과 대화가 서로 다른 소리를 한다.**
- `owned_product_ref` 에 `purchased`(구매 시점)가 없다. 없으면
  "구매 기록을 보니 2023년 5월에 들이신" 같은 출처 표현과 경과 기간 계산을 못 쓴다.
  동작은 하고 출처도 붙는다("구매 기록에 있는 X"). 급하지 않아 요청을 보류했다.
  이건 AI 1 이 아니라 **Backend 에 물을 것** (AI 1 은 받은 값을 그대로 얹는 구조).

### 최종 데모 전 반드시 고칠 것
- 콘솔의 고객 ID 입력은 **개발용 임시 구조**다.
  실제 서비스는 사건(착장 기록 생성, 케어 시점 도래)이 발생하면 시스템이 자동으로
  오프닝을 보내야 한다. 사람이 눌러서 말을 걸게 하면 "AI가 먼저 다가온다"는
  서비스 정체성이 데모에서 죽는다.
  데모 연출도 "고객이 QR 저장 → 그날 밤 메시지 도착"이어야 한다.
