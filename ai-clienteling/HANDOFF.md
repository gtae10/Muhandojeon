# 팀 협의 필요 사항 — AI 2 (상담 에이전트)

AI 2 파트는 동작하는 상태로 완료했습니다.
다만 **혼자 정할 수 없어서 가정을 두고 진행한 것들**이 있습니다.
가정이 틀리면 연동 시점에 고쳐야 하므로 미리 확인 부탁드립니다.

각 항목에 **지금 어떻게 동작하는지**와 **무엇을 정해야 하는지**를 적었습니다.
바쁘시면 ⚠️ 표시된 두 개만 먼저 봐주셔도 됩니다.

---

## ⚠️ 1. `/outreach` — 에이전트가 먼저 말 거는 기능 (Backend · Frontend)

**팀 합의 스펙에 없는 엔드포인트입니다. 제가 추가했습니다.**

### 왜 만들었나

고객이 물어야만 답하는 구조는 공식몰 헬프봇과 같습니다.
"고객이 필요할 때 먼저 다가오는 부티크 직원"이 이 서비스의 컨셉이라,
에이전트가 첫 마디를 건네는 기능을 넣었습니다.


"긴자 매장에서 착장 후 미구매 → 그날 밤 에이전트가 먼저 메시지" 장면입니다.
이 기능이 연동되지 않으면 그 장면이 나오지 않습니다.

### 지금 동작

```http
POST /outreach
{ "customer_id": "C001" }

→ { "reply": "오늘 긴자에서 보신 그 토트, 잘 어울리셨어요. ...",
    "suggested_action": "none" }
```

### 정해야 할 것

**Backend** — 누가 언제 이걸 호출하나요?

실제 서비스라면 **사건이 발생했을 때 시스템이 호출**해야 합니다.
착장 기록 생성, 케어 시점 도래 같은 것들입니다.
지금 콘솔은 사람이 고객 ID를 입력해 호출하는 개발용 구조입니다.

- 트리거를 Backend 가 잡아 호출하는 게 맞을까요?
- 아니면 데모에서는 수동 호출로 가고, 발표에서 "실서비스에서는 자동" 이라고 설명할까요?

**Frontend** — 받아서 띄울 화면이 있나요?

고객이 아무것도 안 했는데 메시지가 도착하는 화면입니다.
일반 채팅 답변과 같은 말풍선이면 되는지, 알림 형태가 필요한지 알려주세요.

**계기가 없으면 400을 돌려줍니다.**
`recent_activity` 도 보유 제품도 없는 고객은 먼저 말 걸 이유가 없어서입니다.
이때 `detail` 은 **개발자용 메시지**이니 고객 화면에 그대로 띄우지 말아주세요.
("착장·조회 기록이 없습니다" 같은 내부 사정을 손님에게 설명하는 꼴이 됩니다)
먼저 말 걸 계기가 없으면 아무것도 안 띄우는 것이 맞습니다.

## 2. `hesitation_type` — 계약 5종에 맞췄습니다 (AI 1)

### 지금 동작

`POST /chat` 과 `POST /outreach` 가 **계약 라벨 다섯을 그대로 받습니다.**
변환하지 마시고 넘겨주세요. 옛 값(`QUICK_EXIT` · `GENERAL_BROWSE`)은 뺐습니다.

| 보내주시는 값 | AI 2 내부 이름 |
|---|---|
| `SIZE_UNCERTAIN` | `fit` (사이즈·수납·실용성) |
| `PRICE_HESITANT` | `price` (가격 대비 가치) |
| `STYLE_DOUBT` | — (기본 응대) |
| `STOCK_CONCERN` | `timing` (재고·시점) |
| `NONE` / `null` / 생략 | — (기본 응대) |

함께 보내주시는 `hesitation_intensity` · `persona_tag` · `talking_point_hint` 는
AI 2 가 쓰지 않아 자동으로 무시됩니다. **보내셔도 오류 안 납니다.**

`STYLE_DOUBT` 만 저희 값에 붙이지 않았습니다. 저희 `fit` 은 "사이즈·수납 불안"이라
치수로 답하는 전략인데, 스타일 고민에 치수를 대면 미적 고민에 숫자로 답하는 꼴입니다.
전용 전략을 만들지는 않았고, 기본 응대로도 잘 나오는 것을 확인했습니다.

**매 턴 보내주셔도 되고 세션당 한 번만 보내주셔도 됩니다.** 아래 이유로,
같은 값이 계속 와도 같은 설명이 반복되지 않습니다.

### 이 값을 저희가 어디에 쓰는지 (2026-08-18 변경)

솔직하게 적습니다. **대화 중(`/chat`)에는 이 값으로 응대 전략을 고르지 않습니다.**

AI 1 분류는 세션 행동이라, 고객이 채팅에서 한 마디도 하지 않아도 값이 옵니다.
그 값으로 전략을 붙이면 고객이 하지 않은 말을 저희가 확인해주는 형태가 됩니다.

  - `price` → "가격이 마음에 걸리시는군요" (부담을 말한 적이 없음)
  - `fit` → 치수·수납·무게를 늘어놓음 (사이즈를 물은 적이 없음)
  - `timing` → "서두르지 않으셔도 됩니다" (조급해한 적이 없음)

셋 다 **"제가 그런 말을 했었나요?"** 를 부르는 형태라 저희 프로젝트에서 가장
피하려는 장면입니다. 그래서 대화 중 망설임은 **고객이 실제로 한 말**에서 잡습니다.

**보내주시는 값이 쓸모없다는 뜻이 아닙니다.** 쓰는 자리가 다릅니다.

| | 무엇에 쓰나 |
|---|---|
| **AI 1 라벨** | 대화 **시작 전** — 누구에게, 언제, 무슨 이야기로 먼저 말을 걸까 (`/outreach`) |
| **고객 발화** | 대화 **중** — 지금 이 사람이 무엇을 걸려 하는가 (`/chat`) |

> 관측한 것으로 **판단은 하되**, 관측했다고 **말하지는 않습니다.**

`/outreach` 에서는 `STYLE_DOUBT` 일 때 첫 마디 다음에 "무엇에 쓰실 건지"
좁혀드리는 질문을 붙입니다. 나머지 값은 계기(착장·케어 시점)만으로 엽니다.

### 여쭐 것 — 이탈 신호를 받을 수 있을까요

옛 `QUICK_EXIT`(세션 클릭 2회 이하)이 계약에서 빠지면서,
**"지금 먼저 말을 걸어야 할 고객"** 을 골라주던 신호가 없어졌습니다.

계약을 되돌리자는 뜻은 아닙니다. 다른 필드로(예: 세션 이벤트 수나 이탈 플래그)
받을 수 있으면 좋겠습니다. "매장에서 보고 그냥 나감 → 그날 밤 메시지"가
저희 데모 대표 시나리오라서요.

**없어도 동작은 합니다.** 지금도 `/outreach` 의 계기는 접점 기록
(착장 저장·장바구니·케어 시점)이 정하고 있습니다. 1번 항목과 함께 봐주세요.

## 4. `suggested_action` 은 글자가 아닙니다 (Frontend)

혼동이 있을 수 있어 명시합니다.

`suggested_action` 은 **화면에 텍스트로 띄우는 값이 아니라 신호**입니다.
카드나 버튼 같은 **모양**으로 바꿔주세요.

| 값 | 의미 |
|---|---|
| `care_booking` | 케어·수선 접수를 제안함 → 접수 버튼 |
| `stock_hold` | 재고 확인·홀드를 제안함 → 확인 요청 버튼 |
| `delivery` | **이미 결제한** 제품의 수령 안내 → 배송/픽업 선택 |
| `staff_connect` | 매장 어드바이저 확인을 제안함 → 연결 요청 카드 |
| `none` | 시스템이 처리할 일 없음 → **말풍선만** |

고객에게 보이는 문장은 `reply` 하나뿐입니다.

## 5. 대화 기록은 호출하는 쪽이 관리합니다 (Backend)

`engine.py` 는 **상태를 갖지 않습니다.**
API 서버가 여러 고객을 동시에 상대할 때 대화가 섞이지 않게 하기 위해서입니다.

그래서 매 요청에 `conversation_history` 를 담아 보내주셔야 합니다.

```jsonc
{
  "customer_id": "C001",
  "message": "이번 발화",
  "conversation_history": [
    {"role": "assistant", "content": "이전 어드바이저 답변"},
    {"role": "user", "content": "이전 고객 발화"}
  ]
}
```

**빠뜨리면 에이전트가 앞 대화를 모릅니다.**
누적 조건(예산 부담 등)도 대화 기록에서 매번 다시 계산하므로,
기록이 없으면 "125만원이 비싸다"고 한 고객에게 185만원 제품을 권하게 됩니다.

저장은 Backend 쪽에서 하시는 게 맞다고 봤는데, 다르게 생각하시면 알려주세요.

## 6. `owned_products` 를 요청에 담으면 우선합니다 (Backend)

CDP 연동을 전제로 만든 경로입니다.

```jsonc
{
  "customer_id": "C999",        // 우리 더미에 없는 ID여도 됨
  "message": "3년쯤 썼는데 핸들이 좀 상했어요",
  "owned_products": [
    { "product_id": "P003",
      "name": "Liz 비세토스 리버서블 쇼퍼",
      "purchased": "2023-05",
      "condition": { "overall": "fair", "notes": "가죽 핸들 마모 진행" } }
  ]
}
```

요청에 담긴 값이 **우리 더미 데이터보다 우선**합니다.
실제 고객 데이터가 오면 그대로 동작한다는 뜻이고,
`tests/test_api.py` 에서 검증했습니다.

Backend 에서 넘겨주실 필드 구조가 위와 다르면 알려주세요.
맞추는 건 어렵지 않습니다.

### 형식이 달라도 죽지 않게 해뒀습니다 (2026-08-17 확인)

AI 1 출력을 실제로 흘려보내며 확인한 것들입니다. **조치는 우리 쪽에서 끝냈고**,
Backend 에서 따로 하실 일은 없습니다. 다만 알고 계시면 좋습니다.

| 들어올 수 있는 값 | 우리 처리 |
|---|---|
| `purchased` 가 `"2023/05/01"`, `"20230501"`, `202305` 등 | 형식 통일. 못 읽으면 필드를 뺍니다 |
| `purchased` 가 `"2023"` (연도만) | 버립니다. 월을 짐작하면 지어내는 것이 됩니다 |
| `product_id` 없이 이름만 | 이름으로 카탈로그와 대조합니다 |
| `condition_score`, `risk` 같은 모르는 필드 | 걸러냅니다 (진단서 화법의 원인) |
| `conversation_history` 의 `content` 가 `null`·키 누락 | 그 항목만 버리고 진행합니다 |

### 두 가지만 지켜주시면 됩니다

**① `owned_products` 는 반드시 리스트로 보내주세요.**
AI 1 은 `owned_product_ref` 를 **단수 객체**로 내보냅니다.
그대로 넘기면 우리 스키마와 안 맞아 **조용히 무시됩니다** — 에러가 안 납니다.

```jsonc
"owned_products": [ { ...owned_product_ref... } ]   // 대괄호로 감싸주세요
```

**② `conversation_history` 를 매 요청에 담아주세요.**
우리는 상태를 갖지 않습니다(동시 요청에 고객이 섞이지 않게 하려는 설계입니다).
빠뜨리면 매 턴이 첫 턴이 되어, 앞에서 한 이야기를 다시 합니다.
이것도 **에러 없이** 대화 품질만 떨어집니다.

### 하나 요청드립니다 — 보유 제품은 목록으로

AI 1 의 `owned_product_ref` 는 **제품 하나만** 담습니다.
그런데 실제 고객은 여러 개를 가지고 있습니다 (우리 더미도 최대 3개).

하나만 오면 나머지는 우리가 모르는 상태가 되고, 그러면
**이미 가지고 있는 제품을 대안으로 권할 수 있습니다.**
실제로 3개를 가진 고객에게 그중 하나를 권하는 것을 확인했습니다.

CDP 에 보유 목록이 있다면 전부 보내주시는 편이 좋습니다.
`purchased`(구매 시점)도 함께 오면 "구매 기록을 보니 2023년 5월에 들이신"
같은 출처 표현을 쓸 수 있습니다. 없어도 동작은 합니다 ("구매 기록에 있는 X").

### 접점 정보에 한 가지 필드가 필요합니다 (CDP 연동 시)

`recent_activity` 에 **`intentional`** (true/false) 을 넣어주세요.

고객이 **의도적으로 남긴 접점**(장바구니·위시리스트·문의·구매·매장 방문)은
에이전트가 언급해도 되지만, **수동 관측**(페이지 조회·체류 시간)은 언급하면
"로그를 봤다"는 뜻이 되어 감시로 읽힙니다.

```jsonc
"recent_activity": {
  "type": "온라인 장바구니 이탈",
  "intentional": true,          // ← 이 값으로 언급 여부가 갈립니다
  "product_name": "Aren 비세토스 스쿨 토트"
}
```

**값이 없으면 수동으로 봅니다** (안전한 쪽). 그러면 장바구니 고객에게도
담아두신 이야기를 못 꺼내므로, 전환 시나리오의 힘이 줄어듭니다.
자세한 근거는 `DESIGN.md` 3절 "무엇을 말해도 되는가" 에 있습니다.

### 관측 메모와 위치는 보내셔도 됩니다 — 저희가 가립니다 (2026-08-18)

**`recent_activity.note`** (예: "가격표를 두 번 확인한 뒤 보류") 같은
행동 관측 메모는 보내주셔도 됩니다. 다만 저희가 **모델의 눈에서 가립니다** —
그대로 두면 "가격표를 두 번 확인하셨던 걸로 보아…" 처럼 고객에게 관측을
말하는 사고가 납니다(실제로 났습니다). 응대 각도를 고르는 판단에는 코드가
원본을 쓰므로, 보내주시는 값이 버려지는 것은 아닙니다.

**`current_location`** 은 저희가 **등록 지역**으로 취급합니다.
"지금 그곳에 계신다"고 말하는 것은 접점이 실제 매장에서 일어난 고객뿐이고,
그 외에는 고객이 대화에서 지역을 말하기 전까지 지역 이름을 꺼내지 않습니다.
GPS 등으로 **현재 위치가 확실한 값**을 주실 수 있게 되면 알려주세요 —
그때는 필드를 나누는 것이 맞습니다.

## 7. `variant` 필드 (Integration · Persona Bot Lab)

응대 전략 비교 실험용으로 넣은 필드입니다. **생략하면 `default`** 라
평소 연동에는 신경 쓰지 않으셔도 됩니다.

| 값 | 내용 |
|---|---|
| `default` | 균형형 (실제 서비스에서 쓸 것) |
| `storytelling` | 헤리티지·서사 중심 |

`control` 은 우리 설계가 실제로 차이를 만드는지 증명하기 위한 것입니다.

비교 스크립트: `python tests/test_variants.py`

## 9. 데모 모델은 `gpt-4o` 입니다 (2026-08-18 mini 에서 전환)

종전에는 mini 였는데 바꿨습니다. **팀 키 비용에 영향이 있어 공유드립니다.**

### 왜 바꿨나

8턴짜리 긴 대화로 스트레스 테스트를 했더니, mini 가 직전 턴의 묻지 않은
제안에 다음 발화를 수락으로 삼켜 **대화가 어긋났습니다**
(고객: "가격이 좀 부담되네요" → mini: "수선 접수를 요청해두겠습니다").
5회 중 2회 재현됐고, 4o 는 같은 시퀀스에서 0회였습니다.

예선이 **제출형**이라 심사위원이 대화를 길게 밀 수 있습니다.
4~5턴짜리 준비된 시나리오면 mini 도 충분하지만, 자유 대화의 완성도는 4o 가 낫습니다.

### 아셔야 할 것 두 가지

- **비용**: 4o 는 대화 1턴에 약 50~60원 (mini 의 약 20배).
  심사 기간 사용량을 팀 키 예산과 맞춰봐 주세요.
- **분당 한도**: 4o 는 분당 30,000 토큰인데 우리 프롬프트가 호출당 약 14,000
  토큰이라 **분당 2회** 수준입니다. 한 명이 순서대로 치면 문제없고
  (사람 타자 속도가 그보다 느립니다), 초과해도 자동 재시도로 이어지지만
  **여러 명이 동시에 돌리면** 대기가 생깁니다. 심사가 동시 접속형이면 알려주세요.

개발·회귀는 계속 mini 로 싸게 돌리시면 됩니다 (`OPENAI_MODEL=gpt-4o-mini`).
코드 기본값은 4o(데모 상태)입니다. 자세한 실행 방법은 `README.md` 를 봐주세요.

## 10. 실서비스 전제로 비워둔 자리

데모에서는 동작하지만 실제 도입 시 채워야 하는 곳들입니다.
발표에서 질문이 나올 수 있어 적어둡니다.

| 자리 | 지금 | 실서비스 |
|---|---|---|
| 매장 정보 | `stores.json` 5곳 (직접 확인) | 매장 조회 API |
| 고객 데이터 | 더미 10명 (가상) | CDP 연동 — 경로는 검증됨 (6번 참고) |
| **재고** | `stores.json` 의 `stock` — **시연용 가정값** | 재고 API |
| **보관(홀드)** | 요청을 전달하겠다는 제안까지 | 매장 예약·홀드 시스템 |
| **결과 회신** | 고객이 되물어야 답함 | **비동기 알림 (Backend)** |
| 먼저 말 걸기 | 사람이 ID 입력 | 사건 발생 시 시스템이 자동 호출 |

### 재고를 가정값으로 넣은 이유 (2026-08-17)

재고 API 가 없어서 처음에는 에이전트가 결과를 **지어냈습니다.**
("확인해본 결과, 재고가 없습니다" — 확인한 적이 없습니다)

지어내게 두면 두 가지가 곤란합니다.
**매번 답이 달라져서** 리허설과 발표가 어긋나고, 매장 위치는 "확인해드리겠습니다"
라고 하면서 재고만 아는 척하면 우리 설계 안에서 앞뒤가 안 맞습니다.

그래서 `stores.json` 에 `stock` 을 넣었습니다. **제품·매장 정보와 성격이 다릅니다.**

| 데이터 | 무엇인가 |
|---|---|
| 제품·매장·헤리티지·서비스 정책 | MCM 공식 자료를 직접 확인한 **사실** |
| 고객 10명 | 해커톤 규칙상 만든 **가상 인물** |
| **재고** | 시연을 위한 **가정값** |

**Frontend 참고** — 재고가 있는 매장을 안내한 뒤 "보관 요청을 넣어드릴까요?"
라고 여쭐 때만 `stock_hold` 가 붙습니다. 여쭙지 않았으면 `none` 입니다.
말로 제안하지 않은 것에 액션만 붙어 승인 카드가 뜨는 일이 없도록 맞춰두었습니다.

**Backend 참고** — 우리는 "요청을 전달하겠다"까지만 말합니다.
매장이 실제로 보관해 주는지, 그 결과를 언제 회신하는지는 우리가 알 수 없습니다.
**결과가 나왔을 때 고객에게 먼저 알리는 것**이 지금 비어 있는 자리입니다.
`/outreach` 가 "계기가 있으면 먼저 말을 건다"는 엔드포인트라,
사건(재고 회신 도착, 케어 완료)이 생겼을 때 호출해 주시면 그 자리를 채울 수 있습니다.

매장 목록을 전 세계로 만들지 않은 이유는,
공식 로케이터가 부정확하고 폐점·팝업이 섞여 있어 확인이 불가능했기 때문입니다.
실제로 확인 과정에서 부산 센텀시티점이 폐점인 것을 발견했습니다.

대신 모르는 지역은 **지어내지도, 없다고 단정하지도 않고**
확인 책임을 에이전트가 가져가는 방식으로 설계했습니다.
자세한 내용은 `DESIGN.md` 3절에 있습니다.

## 11. 컨디션 소견의 "정도" — 역할 분담 공유 (컨디션 모듈 · 2026-08-18)

통합 연동(`/clienteling/reply`)에서 `owned_assets` 의 컨디션 데이터를 받게 되면서,
저희가 이 데이터를 어떻게 다루는지 공유해둡니다. **요청이라기보다 참고입니다.**

### 지금 동작

- `condition_score`(점수)와 `severity`(심각도 라벨)는 **프롬프트에 넣지 않습니다.**
  넣으면 "컨디션 71점, MEDIUM 수준의 마모" 같은 진단서 화법이 나옵니다.
- `findings` 의 **소견 문장**("핸들 마모 진행")만 통과시키며, 그마저
  고객이 케어 화제에 들어오기 전에는 가립니다.
- 어드바이저는 케어가 **필요한지를 판정하지 않습니다.** 제안("살펴봐드릴까요?")까지만
  하고 결정은 고객에게 둡니다.

### 왜 이렇게 나눴나

**정도 판단은 상태를 실제로 측정한 쪽의 몫**이라고 봤습니다. 저희는 그 판단을
고객에게 전하는 쪽이고, 측정하지 않은 저희가 점수를 읽고 필요/불필요를 다시
판정하면 근거 없이 단정하는 것이 됩니다.

### 참고가 될 수 있는 부분

이 분담에서는 **소견 문장이 정도를 담고 있을수록** 저희 답변의 결이 자연스럽게
따라갑니다. 계약 예시의 `"앞창 마모 진행, 재밑창 시점 근접"` 같은 형태가 저희
쪽에서는 그대로 살아요 — 같은 마모라도:

- `"핸들 마모 진행 (일상 사용 수준)"` → 케어를 서두르게 권하지 않는 결
- `"핸들 마모 진행, 수선 시점 근접"` → 접수 제안에 무게가 실리는 결

물론 소견을 어떤 형태로 쓰실지는 컨디션 모듈에서 정하실 일이라, 지금 형태로
주셔도 동작에는 문제가 없습니다.

`severity` · `next_service_months` 를 저희 쪽 **케어 제안 억제 게이트**로 쓰는
방법(숫자·라벨은 문장에 올리지 않고 판단에만 사용)도 가능은 한데, 프롬프트 재료가
바뀌는 일이라 회귀 검증이 필요해 지금은 보류해뒀습니다. 필요해 보이면 편하게
말씀 주세요 — 그때 같이 논의하면 좋겠습니다.

## 12. 통합 연동 스펙 — "한 메종" 세계관 (2026-08-18 저녁, 전 파트)

통합 화면의 어드바이저가 **한 명**이 되도록 재설계했습니다. 데모 픽션을
"하나의 메종"으로 잡으면 fixture 12종도 이 메종의 제품이라, 어드바이저가
**제품 18종(MCM 6 + fixture 12)·고객 16명(C001~C010 + CU-0001~0006)·매장·재고·
배송**을 전부 알고 상담합니다. 기존 C 시나리오(긴자 착장→서울 픽업 등)도
통합 화면에서 그대로 돕니다.

### 엔드포인트 (모두 8102)

| 경로 | 용도 |
|---|---|
| `POST /clienteling/reply` | 계약 그대로. `message`+`cited_asset_ids`+`cta` 반환 |
| `POST /clienteling/outreach` | **어드바이저가 먼저 말 걸기.** `{customer_id, owned_assets?}` — 계기(장바구니 이탈·케어 시점)가 없으면 400 (그때는 화면에 아무것도 안 띄우는 게 맞습니다) |
| `POST /api/chat` | 폴백 경로, 같은 세계관 |

### `cta` 매핑 — 엔진 액션 5종 → 계약 enum 4종 (2026-08-19 갱신)

저희 엔진은 내부적으로 `suggested_action` 5종을 쓰고, 계약 경로에서 이렇게 옮깁니다.

| 엔진 suggested_action | 계약 cta | 비고 |
|---|---|---|
| `care_booking` | `CARE_BOOKING` | |
| `stock_hold` | `VIEW_STOCK` | |
| `delivery` | `NONE` | 대응하는 계약 값이 없어 흘립니다 |
| `staff_connect` | `NONE` | 위와 같음 — 아래 참고 |
| `none` | `NONE` | |
| (해당 액션 없음) | `BOOK_FITTING` | **2026-08-19 추가.** 답변이 실제로 피팅 접수를 여쭙거나 확정한 턴, 또는 피팅 여쭘에 고객이 수락한 턴에만 코드가 판정해 붙입니다. 고객이 거절한 턴에는 절대 안 붙습니다 |
| (해당 액션 없음) | `CARE_BOOKING` | **2026-08-20 추가.** 답변이 케어 예약을 여쭈었는데 엔진 액션이 none 인 턴을 승격합니다 (말과 카드가 같이 가게). 케어 시점 자산(`next_service_months` ≤ 1)이 있는 고객은 표현 형태와 무관하게 답변의 케어 언급으로 승격합니다 — D3 처럼 판정이 cta 를 요구하는 시나리오에서 문구 변형("도와드릴 수 있습니다")으로 NONE 이 뜨지 않게 하기 위해서입니다 |

BOOK_FITTING·CARE_BOOKING 승격은 엔진에 대응 액션이 없거나 빠진 턴의
후처리(문장 판정)입니다 — 놓치는 쪽으로 보수적이라, 피팅 흐름인데 NONE 이
오는 턴도 있을 수 있습니다 (그 경우 화면은 현행과 동일하게 카드 없음).
고객이 거절·보류("생각해볼게요")·맺는 인사("감사합니다")를 한 턴에는
어느 승격도 붙지 않습니다.

참고로 `staff_connect` 는 "지식 밖 질문에 매장 어드바이저 확인을 인수하는"
저희 쪽 신뢰 설계 장치인데, NONE 으로 흘리면 통합 화면에서는 그 카드가
없습니다. 계약 enum 에 값을 하나 늘릴 만한지는 화면을 설계하시는 쪽 판단이라
필요하시면 말씀해 주세요 — 저희는 매핑 한 줄이면 됩니다.

### `cited_asset_ids` 의 뜻 — "답변이 그 자산을 근거로 썼다" (2026-08-20 계약 정렬)

계약 문서의 하드 요구사항("owned_assets 가 있으면 인용 최소 1개")과 데모
시나리오 판정(min_citations)에 맞춰 기준을 넓혔습니다: **저희 답변이 그
자산을 언급했으면 채웁니다.** 같은 라스트 사이즈 근거(D1), 보유 자산 수명
근거(D2), 케어 시점(D3) 전부 카드가 뜹니다 — 데모 3종 × 50회 측정에서
카드 50/50 입니다.

계속 비우는 두 곳은 그대로입니다:
  · **고객만 이름을 꺼내고 저희 답변에는 없는 턴** — 보유와 같은 모델을
    새로 사려는 문의에 마모 카드가 뜨던 사고 방지
  · **출처 추궁 턴** ("그걸 어떻게 아세요?")
빈 배열일 때 카드가 뜨지 않는 전제는 종전과 같습니다.

참고로 통합 데이터에 할인 정책을 한 절 넣었습니다
(`integration_services.json` 의 `promotions` — "상시 할인·프로모션 없음",
시연용 픽션 정책). 할인 문의에 어드바이저가 이 사실로 답하니, 화면·대본과
어긋나면 알려주세요.

### 데이터 동기화 — fixtures 를 고치실 때

저희는 fixtures 를 복사하지 않고 `scripts/build_integration_data.py` 로
**재생성**합니다. `fixtures/products.json`·`customers.json`·`assets.json`·
`session_events.json` 을 고치시면 알려만 주세요 — 스크립트 한 번이면 반영됩니다.

### 시연용 가정값 (알고 계셔야 하는 것)

C001~C010 고객의 자산 ID(`AS-9…`)와 컨디션 점수는 **시연용 가정값**입니다.
이 고객들은 자산 등록 이전에 만든 더미라 실측 점수가 없어서, 재고 가정값과
같은 방침으로 부여했습니다. 발표에서 "확인한 사실 / 가상 인물 / 가정값"
3층 구분을 말할 때 이 항목도 가정값 층입니다.
